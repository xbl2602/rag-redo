## 1. 它长什么样（2026-09-30 第三版）

中心是一颗空心线框恒星，外面每个库一条独立轨道。每条轨道是一根**截面为圆的实心光管**：

```
  ════════════╗        ╔═══════════════════╗     ╔════════
  （细一点）   ╚══════╝  点密的一段略微鼓起  ╚═════╝ （细一点）
   ← 青色渐渐渗进紫色 →      ← 紫色渐渐渗进黄色 →
```

- **管子是连续的**：从头到尾是一根光管，不会断成一颗颗的球。
- **粗细由密度驱动，只鼓起一点点**：语义相近的文件在环上挨得更近，那一段点更密，管子就略微胀粗、更亮；按下面的定版默认值，最密处约为中位粗细的 1.1～1.25 倍，最稀处约 0.8～0.9 倍。
- **轨道半径由点数决定**：点多的库放外圈、点少的放内圈，让每个库管子里的密度都落在合适的区间；相邻轨道之间、最内圈和中心之间都留出最小间距（见第 3 节"轨道与密度"）。
- **起伏极其平滑**：粗细沿环的变化处处可导，没有折角。
- **颜色交融**：相邻主题的点沿环向互相渗进去，交界处是混色，不是一刀切的色块。
- **实心**：截面上管芯最密最亮，往外渐稀。
- **背景不空**：带星云的天空（紫、青、品红的淡云团）、一条带暗尘带的银河、约 1.7 万颗大小和色温各异、会轻微闪烁的星，以及轨道之间一层很淡、缓慢打转的星尘（转视角时有纵深）。

### 这一版是怎么来的（改之前先读）

1. 第一版：整圈等分的扁平环带，密处"略微外凸 + 变亮"。操作者否决：只是某处点多一点，看不出实心、有体积的光。
2. 第二版：把相似文件聚到一个点，用融球（metaball）胀成一颗颗圆光团，串在细管上。操作者否决：**"还有很多地方还是一团球，我认真不要这样的效果，颜色之间的光点是可以混在一起的，不要这样一大团，它应该只是凸起一点点，由密度驱动的。"**
3. 第三版：连续实心光管，粗细 ∝ 密度的小次方，点沿环向散开让颜色交融。
4. 第三版之后，操作者又提了两点：**"拖动那个条的时候页面同步改变，而不是一直刷新"**；**"背景不要那么空"**。
5. 再之后：**按点数判断合适的轨道半径**，避免密度过高或过低，且轨道之间不能靠得太近；并定下了默认值（下表）。本文件描述的就是这之后的样子。

第二版的完整代码备份在会话临时目录里，没有进仓库；如果将来需要"局部成团"的效果，思路记录在第 6 节，不必从头再踩一遍。

### 右上角滑块：全部拖动时同步生效

操作者要求范围**至少上下各放大 10 倍**，所以滑块一律用**对数刻度**：两头能拉到原来的 1/10 和 10 倍，默认值附近仍然调得细。允许 0 的滑块，最左端一格就是 0。

**所有滑块都是拖动时每帧跟着变，点会连续地滑到新位置，从不弹"正在生成"、从不整体刷新。** 只有切换"压力档"（换一批数据）才会重建。

**默认值由操作者在 2026-09-30 定下，之后正式实现也用这一组**：鼓起程度 0.15、聚合强度 5.2、颜色交融 5.0、体积光 0.35，其余外观滑块为 1；轨道与密度：目标密度 2750、密度容许范围 2、轨道最小间距 1、最内轨道离中心 1。

## 2. 怎么做到"同步改变"（核心设计）

一个库的光管由三样东西决定：

| | 是什么 | 什么时候算 | 放在哪 |
|---|---|---|---|
| ① 锚点 | 每个文件沿环的位置（弧长） | 拖"聚合强度"时 | 文件锚点纹理（R32F，一格一个文件） |
| ② 剖面 | 沿环每一处的管半径、相对密度、抹匀后的颜色 | 拖任何形状滑块时 | 剖面纹理（RGBA32F，每库两行 × 1024 格） |
| ③ 偏移 | 每个点相对自己文件的随机偏移：沿环一个高斯数、截面两个高斯数 | **换数据时生成一次，之后永远不动** | 点的顶点属性 |

顶点着色器每帧把三者合成最终位置：

```
沿环弧长 s = 锚点[文件] + 沿环偏移 × 当前散开宽度
管半径 r   = 剖面(s)                      （在 1024 格之间线性插值）
位置       = 轨道方向(s/R + 公转) × (R + 截面偏移x × r) + 轨道法线 × (截面偏移z × r)
```

拖形状滑块时，CPU 先按点数重排轨道半径（见第 3 节"轨道与密度"），再重算 ① ② 并上传两张小纹理（默认档每次约 14 毫秒，这个数是在偏慢的预览窗口里量的；极限档约 8 毫秒，同一帧最多算一次），点的顶点数据一个字节都不动。所以：

- 画面每帧跟着滑块变；
- 点是**连续滑动**的（偏移固定，只是乘的宽度和半径在变），不会像"重新随机撒一遍"那样闪烁乱跳。

体积光同理：每库固定 1024 片方片（第 k 片就在第 k 格），半径、亮度、颜色全从剖面纹理读，滑块改了也不用重建网格。

## 3. 形状算法（`shapeLibrary`，第 245 行起）

### ① 锚点（第 250 行）

相邻两个文件的间距 = `(0.15 + 余弦距离 / 0.5) ^ 聚合强度`，再按比例铺满整圈。顺序是 seriation 的结果，所以角上相邻 = 语义相邻。

- 聚合强度 0：均匀铺开，粗细只随各文件的块数起伏；
- 默认 1：很像的一对间距约 0.21，不像的约 1.15，跨主题约 2.15，密度差五六倍，经过下一步抹匀后是温和的起伏；
- 底数 0.15 是刻意留的：没有它，很像的文件会被挤到一个点上，每个主题缩成一颗单色的球（第二版的问题）。

### ② 沿环密度（第 260 行）

每个文件的权重是它带来的总点数（文件 + 块 + 页），落进 1024 格，再按"点实际散开的宽度"抹开：`σ = √(颜色交融宽度² + (1.5·管半径)²)`。管子粗细跟着点真正落下的地方走，而不是跟着文件中心走。颜色按同样方式抹开，给体积光用。

### ③ 管半径（第 272 行）

```
q = 密度 / 中位密度
x = q ^ (0.6 × 鼓起程度)
x = 平滑max(x, 0.4)，再 平滑min(x, 6)     （p=4 的范数式平滑，处处可导）
r = 管半径 × x，再用 0.5 个管半径的宽度抹一次
```

密度翻一倍，管子粗约 50%。最稀处不细于 0.4 倍（环不断），最密处不粗于 6 倍（安全上限）。

### 轨道与密度（`layoutOrbits`，第 333 行）

**密度的定义**：这个库的点数 ÷ 光管体积。管半径 `r0 = 0.36·√(R/14)·环带粗细·粗细补偿`，体积 `= 2πR·π r0² = ORBIT_VOL_K·R²·(环带粗细·粗细补偿)²`。所以同样的粗细比例下，**等密度的轨道半径 ∝ √点数**：点数翻 4 倍，半径翻 2 倍。

每次形状更新时：

1. **理想半径**：`R* = √(点数 ÷ (目标密度 × ORBIT_VOL_K × 环带粗细²))`。按点数从少到多、从内往外排。
2. **留间距**：相邻两条轨道的管子外沿之间至少留"轨道最小间距"，最内圈的管子外沿离中心至少"最内轨道离中心"。挤的时候两边各让一半（松弛迭代 80 轮），最后再从内往外推一遍，保证约束一定满足。管子外沿 = r0 × κ，κ 是上一次形状算出的"最粗处 ÷ r0"。各轨道倾角不同，但都绕同一个中心：半径差够大，两条管子上任意两点的距离就至少是半径差，不会穿插。
3. **补偿**：为了留间距，某个库被推得偏外（太稀）或偏内（太密），密度跑出 `[目标 ÷ 容许范围, 目标 × 容许范围]` 时，把它的管子调细（太稀时）或调粗（太密时），刚好补到区间边上（补偿系数限制在 0.15–6 倍）。管子粗细变了外沿也变，所以 1–3 步重复三遍；κ 变化超过 5% 时整套形状再算一遍。
4. 公转速度 `0.15·√(8.2/R)`：外圈转得慢。每个库的公转角是**累计**的（每帧加 `dt × 速度`），所以半径和速度随滑块变的时候轨道不会突然跳一个角度。轨道参考线是单位圆，按当前半径缩放；库名跟着半径移动。

关掉"按点数自动排轨道"时，回到 `LIB_DEFS` 里写死的半径，不做补偿。

### 换数据时做一次的（`prepareLibrary`，第 208 行；`buildAll` 第 882 行）

- 相邻文件的语义距离、每个文件的点数和颜色；
- **松散度**：文件与左右邻居质心的余弦相似度，越不像越暗（最多暗 22%）。原版这一项多除了一次邻居个数，结果恒≈0，从没生效过，已按注释本意修正；
- **每个点的固定偏移**：沿环 = 截在 ±3 的高斯数；截面 = 宽 0.45、截在 0.97 的二维高斯（单位是当地管半径），所以管芯最密最亮。块和页各自独立落点：它们是点的大头，颜色能不能混开主要看它们；
- 越密的地方单个点越暗（`q^-0.5`，在着色器里按当前剖面算），叠加后仍然是"管芯发白、往外带色"。

### 可调常量（第 135–155 行）

| 常量 | 默认 | 作用 |
|---|---|---|
| `TUBE_R0` | 0.36 | 中位密度处的管半径（标定半径 14 处，按 √(R/14) 缩放） |
| `BULGE_K` | 0.6 | 鼓起指数：管半径 ∝ 相对密度^(0.6 × 鼓起程度) |
| `THIN_FLOOR` / `THICK_CEIL` | 0.4 / 6 | 最细 / 最粗相对管半径的倍数（平滑收住） |
| `GAP_FLOOR` | 0.15 | 间距底数：越大越均匀，越小越按语义挤 |
| `DENS_BINS` | 1024 | 沿环采样格数。拖滑块时每帧要重算，够用就好 |
| `SIZE_FILE` / `SIZE_CHUNK` / `SIZE_PAGE` | 0.065–0.14 / 0.034 / 0.026 | 点的世界直径。点要比管子细得多，轮廓才顺 |

## 4. 渲染

- 数据是两个主 draw call：所有点一个 `THREE.Points`，体积光一个实例化网格。点和体积光共用一段着色器代码 `SHAPE_GLSL`（读库参数、在剖面上插值）。
- 体积光：管子粗时相邻方片重叠太多，只保留每 m 片中的一片（m 取 2 的幂，保持约 4 层重叠），亮度按 m 补回。片元 = `(1−b²)^0.75` 的体积厚度 + 窄的发白内核 + 很薄的外晕。
- 十字星芒**只给文件点**，块和页不要，否则近看是一片闪粉。
- **混合模式必须是"纯加色、不写画布透明度"**（`ADD` 对象：颜色 One/One，透明度 Zero/One）。three 自带的 `AdditiveBlending` 会把透明度也叠满，画布在方片覆盖的范围里变成不透明黑，背景渐变被挖出一个个黑圆盘。
- 公转角按每个库**累计**（`rot += dt × 公转速度滑块 × 这个库的速度`），通过 `uLibB.x` 传给着色器，而不是"时钟 × 速度"：拖速度滑块、或者轨道半径变了导致速度变了，轨道都不会跳。星尘仍用全局的累计时间 `uTime`。

### 背景（第 625 行起）

| 层 | 做法 | 跟谁走 |
|---|---|---|
| 天空 | 半径 1400 的内翻球，片元里用 3D 值噪声的 fbm 画星云（紫 / 青 / 品红三色按另一层噪声混），沿一条大圆加银河的弥散光和暗尘带，再加一层极淡的全天底光 | 跟着镜头（永远在无穷远，只随视角转） |
| 远星 | 9000 颗全天均匀 + 8000 颗集中在银河带；亮度幂律分布（大多暗、偶尔很亮），色温从蓝白到橙；各自不同频率轻微闪烁；大的带小十字芒 | 跟着镜头 |
| 星尘 | 6000 颗极淡的微粒，分布在半径 3–34 的厚盘里，内快外慢缓慢打转 | 在场景里，转视角时有视差 |

三层亮度都受"背景亮度"滑块控制。闪烁用真实时钟，不受公转速度影响（公转停了星星照样闪）。

## 交互

`OrbitControls`：左键旋转、滚轮缩放、右键平移。悬停拾取仍然是"角楔包围球粗筛 → 逐点算与射线的距离"，点的位置在 CPU 上用和着色器同一套公式重算（锚点 + 固定偏移 × 当前宽度 / 管半径），所以和画面完全一致。角楔在每次形状更新时按新锚点重建；起点随机，所以一个楔可能被拆成两段，粗筛不受影响。

调试钩子（只在 demo 里）：`__libs()`、`__U`、`__applyShape()`、`__cam(x,y,z, tx,ty,tz)`、`__focusBead(库序号, 第几粗, 距离)`。

（"1.36×"是密度 ÷ 目标密度。最内圈管子外沿到中心的距离在各档都 ≥ 4.0。）

其他已确认（在预览窗口里）：

- **拖动"目标密度"**：从约 2700 连续拖到约 380，共 20 步，Obsidian Vault 的轨道半径从 9.0 连续变到 23.6，全程没有刷新，间距约束每一步都满足。
- **拖动同步**：用脚本每 30 毫秒推一次"鼓起程度"滑块，从 1.09 推到 6.20，共 20 步，画面每步都跟着变，全程没有出现"正在生成"，帧率保持 60。
- 形状重算耗时（含排轨道）：默认档中位约 6 毫秒，极限档约 6 毫秒。
- 三档（×1 / ×2.4 / ×5）都能生成、来回切换无报错（切换时文件锚点纹理会换尺寸，见第 6 节第 1 条）；构建约 0.15–0.45 秒。
- 所有滑块拉到最左、最右，管半径都没有出现 NaN。
- 悬停提示正常。
- 抹匀函数 `smoothWrap` 用 node 单独和精确高斯对拍过：σ ≤ 64 格误差 < 1% 峰值，更宽时（滑动平均近似）约 5%，总量守恒，超宽时退化为整圈平均。

移植到正式实现时，建议把这几条做成断言：

```
管半径剖面处处有限、一阶差分连续（衔接光滑）
中位 ≈ 1，最粗 ≤ 2.5，最细 ≥ 0.4（只鼓起一点点、环不断）
每个点沿环向偏离所属文件 ≤ 3 倍交融宽度，截面上在管壁以内（有界）

形状更新不修改任何顶点数据（只改纹理和 uniform）
自动排轨道后：相邻管子外沿间距 ≥ 设定值，最内圈外沿到中心 ≥ 设定值，每个库密度 ∈ [目标÷容许, 目标×容许]
```

**没验证的**：真机帧率和真机上拖动的手感；实际观感只在预览窗口里看过，需要操作者在自己的屏幕上看。

## 6. 踩过的坑（改代码前先读这一节）

本轮（按点数排轨道）：

0. **公转速度随半径变，不能再用"时钟 × 速度"算角度**：半径一变，速度一变，整条轨道会突然转过去一大截。改成每个库累计角度。每个库的随机起点也改成按"整圈的比例"存（轨道周长会变）。

上一轮（同步改变 + 背景）：

1. **three 在 WebGL2 下用不可变存储（`texStorage2D`）**，一张纹理之后只能按原尺寸更新。换压力档时文件数变了，锚点纹理要换尺寸，必须先 `dispose()`，否则直接报错。
2. **"拖动时每帧重建"不等于同步改变。** 如果每次都重新随机撒点，点会闪烁乱跳。必须把随机偏移固定下来，只让宽度和半径变。
3. **拖滑块时最贵的是沿环抹匀里的取余运算。** 已改成首尾补齐后线性卷积、四条数组一起处理，采样格从 2048 降到 1024，重算从约 70 毫秒降到约 14 毫秒（预览窗口里）。
4. **形状更新要合并到帧里**：`input` 事件只打标记，下一帧 `tick` 里最多算一次，拖得再快也不会堆积。
5. **公转时间要累加**，见第 4 节。
6. **预览窗口被隐藏时 `requestAnimationFrame` 不走**，用脚本测拖动时要注意，别等帧回调。

第三版：

7. **把相似文件挤到一个点 = 每个主题一颗单色球。** 间距一定要留底数（`GAP_FLOOR`）。
8. **颜色要能混，块和页必须各自独立落点。**
9. **滑块范围放大后，抹匀的宽度可以比整圈还宽**：直接卷积会卡死页面，环形下标还会越界成 NaN。已改成大 σ 用滑动平均。

第二版留下的、以后可能还用得上的：

10. **想要局部成团时，不要事后给半径封顶**：粗细被卡住而长短不受限，鼓包会变成橄榄形。
11. **团圆不圆取决于团内文件的散布是否远小于抹匀宽度**，散开一个抹匀宽度就是柠檬形。
12. **点只约束在管内，团里的点会顺着细管漏出去**，远看拖尾像米粒。
13. **three 的 `AdditiveBlending` 会写画布透明度**，见第 4 节。
14. **密集处单个点要按密度降亮度**，否则过曝成白片。

沿用的旧坑（仍然有效）：

15. **`WireframeGeometry` 不带 `normal`**，法线要从 `position` 自己算。
16. **`Int32Array.prototype.map` 返回的还是 `Int32Array`**，要返回对象必须 `Array.from(seq, fn)`。
17. **所有散布都必须有界**：显式裁剪。高斯本身无界。
18. **幂迭代欠收敛会让小库的语义排序变差**（`PITERS` 要留够）。
19. **改名字要一次改全**，改完 grep 旧名。
20. **滑块回调要重算投影比例**（`uSizeK` 里含点大小）。

## 已知取舍

- 数据是合成的：主题 → 子团 → 文件，紧/松各半，块数和页数是长尾随机。**没有接真实 `graph()` 契约。** 真实语料的密度起伏有多大，决定了默认"鼓起程度"是否合适，需要用真实库再看一遍。
- 三档压力档是把库规模乘 `sqrt(k)`（大库）或 `k`（小库）造出来的。
- 拾取容差仍是固定的世界单位（0.05），放大很近时可能需要按距离缩放，没做。
- 颜色交融是沿环向的"渗透"，不会把环上相隔很远、但语义相似的两处拉到一起；这是有意的，否则环就不是环了。
- 背景的星云、银河、星尘是纯装饰，不代表任何数据。

## 7. 落到正式实现前的门槛（**需要操作者拍板，agent 不要自行决定**）

1. **BC-15 要修订。** `plugins/official-gui-shell/official_gui_shell/assets/` 下的 `app.js` / `app.css` / `index.html` / `mock.js` 目前被 `plugins/official-gui-shell/tests/fixtures/legacy_guiweb_contract.json` 按 **sha256 + 字节数**钉死为旧项目 `obsidian-rag/guiweb/ui` 的逐字节复刻。总览页是 `app.js` 第 1799 行起的图谱引擎（`G` 对象 + SVG 力导向）。换掉它等于改已登记行为，必须走 `AGENTS.md` §3.3 确认流程，并同步更新固定值与 `docs/behavior_contract.json`。
2. **块级、页级点位数据现在拿不到。** `contract_bridge.py::graph()` 返回的文件级字段里，`chunks` 只是**计数**，不是块列表；页级（WEMM）节点也没有向量。本方案还需要**文件级向量**（用于排序和间距）。这些都要新开契约方法（读向量库 + 页库），属于新增功能，得先补 `BC-*` 与验收标准。
3. **前端要本地化 three.js。** 正式资产不能走 CDN（本地优先、离线可用），得把 three 打进 `assets/` 并计入便携包体积；`installer/build_windows.py` 会整体打包 `plugins/`，新增依赖要同步 `README.md` 的安装说明。
4. **GUI 仍是零业务判断的观察者**（`AGENTS.md` §8.4）。上面这些算法只能放在前端或对应插件里，桥接层只提供数据。
5. **配色、管子粗细、鼓起程度、颜色交融宽度、轨道排布规则、背景都是用户可感知的外观**，一旦定版就要登记进行为契约。全部默认值（见第 1 节表格加粗项）已由操作者定为正式实现的默认值。
6. **需要 WebGL2。** 正式实现要确认目标机器（含便携包内嵌的浏览器内核）都支持，或者准备退路。
7. **构建耗时**：语义排序是最慢的一步，正式实现应放进 Web Worker，或把排序结果随索引缓存。
