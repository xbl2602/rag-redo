# 数据流治理原则

## 单向管道，不是网状乱连

数据该怎么流动是提前设计好的：发现 → 抽取 → 切块 → 向量化/词法化 → 写入 → 后处理。这条流水线的方向是固定的，没有反向箭头，不能"比对模块回头去改分类结果"这种事。

## 禁止事项

- 插件之间不能互相 import 或直接调用对方的代码，只能通过核心编排的管道交换数据。
- 界面不能抄近道，只能调用核心暴露的查询/命令接口，不能直接连数据库。
- 跨插件传递的数据格式只能用核心定义好的类型，不能私下发明字段名。
- 同一件事的标准答案只能在一处定义，比如"一个文件算不算在检索范围内"只在 library-manager 插件里判定一次。

## 为什么要这么严格

如果数据"哪里方便就从哪流"，很快会出现：改了某个模块的输出格式，另一个模块悄悄跟着坏掉，但因为两边是直接互相调用而不是通过统一类型定义，排查起来根本不知道问题出在哪一环。管道式设计的好处是，出问题时顺着固定路径查，永远知道该去哪一环找错。
