# 数据流规划

> 数据该怎么流动是提前设计好的，不是"哪里方便就从哪里接一根线"——这条原则和方法论直接借自参考模板项目（Averis-Monash-Hackathon-2026）的同名文件，事实证明团队并行开发+多个AI session同时改代码的场景下，这条纪律是唯一能防止"改了A模块，B模块悄悄跟着坏掉却查不出为什么"的办法。RAG REDO 是插件化架构，比那个模板项目的"文件夹隔离约定"更进一步——插件之间物理上可能完全不知道彼此的存在（甚至不同进程/不同语言），这条规则因此更不能是君子协定，必须由 [ARCHITECTURE.md](ARCHITECTURE.md) 第2.2节的数据流管理器强制执行。

## 核心原则

**插件之间不能互相直接调用。数据只能通过核心编排的管道流动，格式只能用核心定义的契约。**

## 索引态管道（从一个 Vault 文件到可检索状态）

```
[library_manager 插件] 判定哪些文件在范围内（decide_included）
        │
        ▼
[extractor:<ext> 插件] 文件 → 纯文本/Markdown（可能是OCR）
        │  失败一律折叠成 (None, reason)，绝不抛异常——继承旧项目架构红线1
        ▼
[chunker 插件] 文本 → 有重叠的语义块
        │
        ▼
[embedder 插件] 块 → 向量                      [lexical_index 插件] 块 → 词法索引条目
        │                                              │
        ▼                                              ▼
[vector_store 插件] 写入                        （由数据流管理器统一落库，不是embedder/lexical_index插件自己开库文件写）
        │
        ▼
[dedup / visual_index 等后处理插件] 各自独立跑，互不阻塞主链路失败
```

方向固定：发现 → 抽取 → 切块 → 向量化/词法化 → 落库 → 后处理，没有反向箭头。

## 查询态管道

```
查询文本
   │
   ▼
[lexical_index 插件检索] ──┐
                          ├──▶ [fusion 插件：RRF] ──▶ [reranker 插件] ──▶ 标注/建议 ──▶ 响应
[embedder+vector_store 插件检索] ──┘
```

## 数据流规则（禁止事项）

1. **插件之间不能互相 import 或直接调用对方的代码**。`extractor` 插件的代码不能引用 `embedder` 插件内部的任何东西，反过来也不行——上一个阶段的输出是下一个阶段的输入，中间由数据流管理器传递，插件不主动"伸手"找别的插件要数据。
2. **GUI 插件不能抄近道**。`gui_panel` 插件只能调用核心暴露的查询/命令 API，不能在前端代码里直接连数据库、直接调某个具体插件的内部实现。
3. **跨插件传递的数据格式只能用核心 `contracts` 模块里定义好的类型**，不能在某个插件里临时发明一个新字段名然后口头/文档告诉其他插件作者"记得用这个格式"——必须是代码里真的引用那个类型定义。
4. **同一件事的标准答案只能在一个地方定义**。比如"一个文件算不算在库的检索范围内"这个判定，只在 `library_manager` 插件（或它向数据流管理器注册的判定函数）里出现一次，其他插件都是查询这个判定结果，不能各自维护一份"我猜它应该被排除"的逻辑。这条直接继承旧项目 `library.decide_included`"裁决唯一实现"的教训（旧项目问题44/47附记2的踩坑记录）。
5. **插件不直接读写持久化存储**。向量库、词法索引、库配置、插件启用状态——统一通过数据流管理器的 DataStore API，插件按自己声明的扩展点类型拿到收窄过的读写权限（一个 `extractor` 插件不该有 `vector_store` 的写接口）。

## 数据的读/写边界（草案，随Phase 0实现细化）

| 数据 | 谁能读 | 谁能写 |
|---|---|---|
| 库配置（哪些库、勾选了哪些路径） | 所有插件（只读视图） | 只有 `library_manager` 插件通过 DataStore 写；Agent 触发的修改必须过写权限门禁（见 ARCHITECTURE.md 2.2） |
| 向量库 / 词法索引 | 检索相关插件（只读查询接口） | 只有索引态管道自己（数据流管理器编排），任何插件都不能绕过管道直接写 |
| 插件启用状态 / 配置 | 插件管理器 UI、CLI | 只有插件运行时（用户在 GUI/CLI 操作触发） |
| 提取缓存 | 对应 `extractor` 插件自己 | 同左，且必须遵守终态落盘纪律（不产块的文件必须落终态，避免每轮误判 stale——继承旧项目架构红线2） |
| 插件的私有配置命名空间 | 该插件自己 | 该插件自己（通过 ctx，其他插件拿不到） |

## 编排层

数据流管理器内部有且只有一个"知道顺序"的编排组件，所有触发索引/查询的入口（GUI、CLI、MCP）都调它，不在各自入口里重新拼一遍"先抽取再切块"这种顺序逻辑。
