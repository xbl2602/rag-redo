# 架构教训（从旧项目提炼）

> 旧项目 [TASK_LOG.md](legacy/TASK_LOG.md) 记录了54个编号问题、27万字的真实踩坑史，原文整份归档在 [docs/legacy/](legacy/)。这份文件是从旧 `AGENTS.md` 的"架构红线"章节+TASK_LOG 标题反推出的精炼版——把当时"为什么这条规则存在"的教训，重新表述成插件架构下依然成立的设计规则。这是首版提炼，不是逐条翻译，后续实现中如果发现某条旧教训在新架构下有不同的体现方式，欢迎补充/修正这份文件。

## 1. 失败必须折叠成诚实的终态，不能裸抛异常

旧教训（架构红线1/2）：`extract_to_markdown` 绝不抛异常，一切"不产块的文件"必须落持久化终态，否则每轮都会被误判成"没处理过"而死循环重试。

新架构下的体现：插件运行时的 `on_load`/`on_enable` 等生命周期钩子全部在 try/except 边界内，失败折叠成插件状态 `failed`+可读原因，不传播成宿主进程崩溃。数据流管理器要求索引态管道里每个阶段对"处理失败"有明确的终态语义（不是简单地把失败当成"暂时没处理"），具体 schema 在 Phase 0/1 实现时确定。

## 2. 一件事的判定逻辑只能有一处实现

旧教训（问题44/47附记2）：文件该不该被检索到的判定（`decide_included`）一旦出现"显示用一份、建索引用另一份"的隐患，就会导致界面看到的和实际生效的对不上——这类 bug 极难排查。

新架构下的体现：DATA_FLOW.md 规则4，同一件事的标准答案只能在一处定义（比如"库范围判定"只在 `library_manager` 插件里），其他插件只能查询结果，不能各自维护一份影子逻辑。

## 3. 版本号是"要不要重算"的唯一信号，改逻辑必须动版本号

旧教训（架构红线5）：改切块/清洗逻辑必动 `META_VERSION`，改提取逻辑必动 `EXTRACT_VERSION`，否则旧缓存会被误当成"新逻辑处理过的结果"继续使用。

新架构下的体现：每个插件在 manifest 里的 `version` 不只是给人看的——数据流管理器在索引态管道里会把"产出这份数据的插件版本"记进契约元数据，插件版本变化足以触发对应阶段的数据判定为"过期需要重算"，具体触发范围（是这个插件自己的数据过期，还是连累下游）在 Phase 1 按扩展点类型细化规则。

## 4. GPU/独占资源的仲裁必须 fail-open，且给的是快照不是租约

旧教训（架构红线9，问题41）：显存探测失败绝不能阻塞任何路径；"先腾显存、稍后再加载"这种交接之间的窗口期，别的请求可能已经把资源抢回去了——仲裁给的是某一时刻的判断，不是保证到用完为止都不会变的承诺。

新架构下的体现：ARCHITECTURE.md 2.1节的资源仲裁器原语必须把这条焊死——申请到的锁在释放前持有，但任何"探测/判断"类调用失败时默认放行而不是默认拒绝，这个原语只写一次，所有 `subprocess_service` 插件复用，不用每个插件自己重新踩一遍这个坑。

## 5. 一次性/仅供预览的旁路工具，不能悄悄绕开用户配置的隐私开关

旧教训（架构红线7，2026-08-25 council 审计）：一个"仅供预览"的提取试验台复用了正式索引相同的缓存目录，导致一次性的手动测试在用户不知情下变成了正式生效的内容——云端 OCR 测试过的文件，即使配置是 `backend=none`，索引时也会命中那份测试产生的缓存。

新架构下的体现：插件的私有状态必须显式声明隔离（ctx 暴露的存储 API 天然按插件命名空间隔离，见 PLUGIN_SPEC.md 第3节 ctx 定义），任何"临时/测试用途"的代码路径如果需要复用正式数据目录，必须在 contracts 里显式标注"这是测试路径"，数据流管理器有责任防止测试数据污染正式判定——具体机制 Phase 1 实现时细化，但这条原则现在就定下来，避免重蹈覆辙。

## 6. GUI 必须是零侵入的观察者

旧教训（架构红线7）：GUI 不加载模型、不直写数据库，进程治理有专门的关闭方式，不能被单杀 PID 导致孤儿进程。

新架构下的体现：`gui_panel` 扩展点的插件禁止直接持有 DataStore 的写接口或直接 import embedder/vector_store 之类的重型插件——这条已经写进 DATA_FLOW.md 规则2，这里额外强调进程治理：`gui_panel` 如果需要独立进程（比如 pywebview 壳本身），必须遵守插件生命周期的 `on_disable` 语义，不允许留下杀不干净的孤儿进程，这是旧项目问题19b/42踩过的坑。

## 7. API Key 等敏感值，错误信息只含类型和摘要，绝不进日志

旧教训（架构红线8）：MinerU 客户端的错误消息只含类型与摘要，不透传上游原文。

新架构下的体现：`permissions.network` 声明为 true 的插件如果同时涉及密钥类配置，数据流管理器对这类插件配置命名空间要有"敏感字段"标记（借鉴参考模板项目里加密存储+只回掩码不回显明文的做法），具体存储加密方案 Phase 3 做 `official-ocr-mineru-cloud` 时定型。

## 8. 两份本该一致的状态一旦分叉，不能靠人工发现——要能自愈

旧教训（TASK_LOG 问题14/16/22-F7/26/39/46等反复出现）：Chroma 实际块数与 meta 记录的期望块数对不上、`_version` 顶层键破坏遍历语义、WEMM 失败终态"记入待重试却没有真正的重试机制"——这些都是"两份本该一致的状态悄悄分叉"，轻则每次搜索都误报 stale 陷入死循环重建，重则永久停摆（旧项目内部管这种终态叫"死寂"）。最终方案是通用规则：任何两处本该一致的计数/状态一旦检测到分叉，自动判定为"整体不可信"并触发权威重算，不是逐处打补丁守卫。

新架构下的体现：这比本文件第3条"版本号触发重算"更进一步——版本号处理的是*已知*的逻辑变更，这里处理的是*未预期*的静默漂移。数据流管理器对"缓存/索引态 vs 权威源"的一致性校验应该是核心提供的通用机制（比如 vector_store 的实际条目数和 library_manager 记录的期望文件数对不上时如何处理），不能让每个插件各自发明校验逻辑，否则每个插件都会在自己那一层重新踩一遍这个坑。

## 9. 重建/替换类写操作必须"先备好新数据、再原子切换"，绝不能先破坏旧数据

旧教训（问题2、问题7 Bug C、问题34"宁可诚实空缺不留半份"）：`--full` 全量重建曾经先 `delete_collection` 清空库再慢速重建，中途中断就是数据归零；后改成先在锁外把全部新向量算完，真正进写锁后才做 delete+upsert，真空窗口从"整个重建耗时"缩到毫秒级。

新架构下的体现：数据流管理器的索引态管道对"全量重建"类操作要有统一原语——先产出完整新状态、再原子切换，任何插件（`vector_store`/`lexical_index`）都不能自己发明"先清后建"的写法。这是数据完整性红线，比 DATA_FLOW.md 目前"插件不能绕过 DataStore 写"这条更具体一层：不仅要通过 DataStore 写，写的**顺序**本身也有唯一正确答案。

## 10. 独占资源耗尽不一定会抛异常，仲裁器需要能感知"反常变慢"而不只是"分配失败"

旧教训（问题14，8GB显存溢出到共享内存导致处理速度骤降400倍却零报错）：Windows WDDM 显存溢出会静默把多出来的部分排入系统内存，不是抛 OOM 异常——"捕获异常再降级"这套机制在这种场景下完全失效，唯一能观察到的信号是"处理速度反常变慢"，最终方案是"连续 N 批耗时超阈值"的看门狗主动触发降级。

新架构下的体现：本文件第4条"资源仲裁器必须 fail-open、给的是快照不是租约"说的是仲裁器**主动探测**时的策略；这一条是仲裁器**被动感知**资源耗尽的另一半——插件可以向资源仲裁器上报"这一批处理耗时异常"，仲裁器据此触发让路，不能假设"资源耗尽必然会通过异常暴露"，这在 GPU/显存这类场景下是错误假设。

## 11. 并发调用同一独占资源，仲裁原语需要"单飞去重 + 互斥 + 忙时否决"，不是让调用方阻塞硬等

旧教训（问题59，多 Agent 并发调用 MCP 触发的 GPU 调度重构）：多个 Agent 同时触发检索/索引会导致模型重复加载、显存互斥判断出现竞态；最终方案是一把全局可重入锁包住"改变资源占用状态"的操作（加载/释放/驱逐判定），锁内做二次检查防止重复加载（单飞去重），纯查询类操作不持锁、天然可并发；碰撞时优先返回"忙，稍后再试"，不是让调用方长时间阻塞等待。

新架构下的体现：`core/gpu_arbiter.py`（本轮新增）的 `GPU_LOCK` 已经落地了"变更状态的操作持锁、纯查询不持锁"这一半；"单飞去重"和"忙时否决而非无限等待"是这条教训里还没有专门落地验证的另一半——面向未来可能出现的"多个 Agent 通过 MCP 并发调用同一个库的索引/检索"场景，这应该是资源仲裁器 v1 设计时就该定下的接口形状，不是发现问题后再补的优化。

## 12. 进程存活探测必须用平台正确的只读原语——选错的后果是探测者亲手杀掉被探测的进程

旧教训（问题22 F5）：`os.kill(pid, 0)` 在 Windows 上不是"探测"——CPython 在 Windows 下把非 CTRL_C/CTRL_BREAK 的信号值直接传给 `TerminateProcess` 当退出码，`sig=0` 也不例外，这意味着"探测一下这个进程还活不活着"这行代码本身就会真的杀死目标进程。旧代码里单例守卫、锁超时清理、GUI 主循环的"探活"调用因此会误杀正在服务的进程或自己拉起的子进程。

新架构下的体现：这条本轮已经在实践中验证过——`core/subprocess_service.py` 与各插件测试里的存活探测统一改用 Windows 下 `OpenProcess`（只读访问权限）+ `WaitForSingleObject`/`CloseHandle` 的组合，不用 `os.kill`。这里补记的是"为什么"：这是会在代码评审中被轻易忽略、一旦踩中就是"仲裁器/守护逻辑自毁其守护对象"的静默灾难，任何新增的"判断某进程是否存活"的代码都要显式检查一遍这条。

## 13. 长时间后台任务需要独立的心跳/进度可观测通道，不能靠"锁是否被占用"或轮询返回值猜死活

旧教训（问题13，索引卡死但没有进度可见，15分钟被误判为正常在跑，后续演化出定时心跳+双重停滞判定+宽限期机制）：光靠"这个操作还没返回"判断不出"它是在正常干活"还是"已经卡死"，必须有独立的、持续更新的进度信号。

新架构下的体现：`subprocess_service` 与任何长时间索引编排操作，理想情况下应该有核心统一提供的"进度/心跳上报"契约（阶段、完成度、最后心跳时间），供 GUI/CLI/MCP 一致地判断"在正常跑"还是"卡死"，而不是每个插件自己决定要不要上报、上报成什么格式。这是插件生命周期管理之外、数据流管理器该管但目前 PLUGIN_SPEC.md 完全没有覆盖的一块，暂不属于当前阶段的实现范围，先记录下来。

## 14. 多层子进程结构的清理必须逐层认领 PID，杀父进程不保证子孙进程一起消失

旧教训（问题19b/19c GUI三层进程残留、问题51附记 MinerU 壳套子进程孤儿显存）：无论是 GUI 框架的三层进程嵌套，还是 MinerU 壳进程套着的内部子进程，强杀外层进程后，Windows 上内层进程不会自动跟着死——必须由启动方自己记录内层真正的 PID，退出时逐层主动认领回收；认不出宁可残留，也不能瞎猜误杀无关进程。

新架构下的体现：这是本文件第6条"GUI 零侵入观察者"和 AGENTS.md 架构红线6"不产生游离进程"的关键补充——本轮 `core/subprocess_service.py::_kill_process_tree` 用 `taskkill /F /T` 处理的正是"venv 的 python.exe 自己又派生一层子进程"这个真实案例，是这条教训在当前架构下的具体落地；如果将来某个 `subprocess_service` 插件自己内部还会再派生子进程（比如未来某个模型服务套壳调用另一个真正的推理进程），这条教训要求 `on_disable` 的清理逻辑必须显式追踪到那一层真正的 PID，不能假设"杀掉我直接启动的那一个进程就够了"。

## 15. 配置/清单默认值只能有一处权威来源，两份手工维护的默认值表迟早互相矛盾

旧教训（问题22 F2）：`DEFAULTS` 常量表与配置模板注释里手写的默认值长期存在不一致，导致某次真实改进过的默认值在下次启动时被悄悄回退到旧值，且每一份分发副本必然踩中——不报错，只是行为悄悄变回旧的，比直接崩溃更难排查。

新架构下的体现：这和本文件第2条"业务判定逻辑只能有一处实现"是同一类问题在配置/schema 层面的翻版，后果更隐蔽。`plugin.toml` 字段的默认值和插件模块里硬编码的常量（本项目"无配置系统，插件用模块常量做配置"的既定约定，见 AGENTS.md）必须只有一处代码路径能改——不能出现"manifest 校验逻辑里有一份默认值假设、插件模块常量里又是另一份"这种两处手工同步的写法。目前插件数量还少、常量集中在各插件自己的模块里，暂时没有真正踩中这个问题，但插件数量增多后复现概率会上升，值得提前记在这里。
