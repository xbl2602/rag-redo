# 架构总览

> 这份文件定义 RAG REDO 的核心架构：两个核心组件是什么、为什么只有两个、插件怎么接进来。改代码前先看这份文件，和 [DATA_FLOW.md](DATA_FLOW.md) / [PLUGIN_SPEC.md](PLUGIN_SPEC.md) 同级——这三份是硬性规则，不是背景介绍。

## 0. 从哪来

RAG REDO 是 obsidian-rag 项目的完全重构，不复用旧项目的代码或数据，但复用它验证过的**算法与模式**（混合检索的 RRF 融合、GPU 显存仲裁的抢占策略、Agent 写权限的两段式确认门禁、子进程隔离重型依赖……这些不是推倒重来的对象，是已经用真实用户、真实 bug 验证过的设计，值得原样搬过来，只是要重新套进插件边界里）。旧项目的问题不在于这些算法不好，而在于：所有东西挤在几个几万行的文件里（`index.py` 122KB、`server.py` 57KB），换一个 embedding 模型、加一种文件格式，都要改核心文件；这正是本项目要解决的问题。

## 1. 五条约束，及它们怎么落到架构上

1. **安装极简化** → 见 [PLUGIN_SPEC.md](PLUGIN_SPEC.md) 的分发形态 + 本文件第5节"重型依赖怎么办"
2. **架构插件化，核心只剩两个组件** → 本文件第2、3节
3. **数据流统一管控** → 见 [DATA_FLOW.md](DATA_FLOW.md)
4. **依赖关系独立** → 第5节 + PLUGIN_SPEC.md 的 `runtime.kind`
5. **Windows 主战场，Linux 能开发** → 不影响架构设计，是打包与 CI 层面的约束，见 [ROADMAP.md](ROADMAP.md) Phase 4

## 2. 两个核心组件

真核心只有两样东西，除此之外的一切——检索算法、embedding 模型、OCR、GUI、MCP 协议服务——都是插件，只是"官方默认安装包"会预置一组插件让开箱即用。

### 2.1 插件运行时（Plugin Runtime）

负责插件的发现、校验、加载、生命周期、以及**跨插件的资源仲裁**。具体职责：

- **发现**：扫描 `plugins/*/plugin.toml`。发现是**显式触发**的（启动时一次，或用户在插件管理器里点"重新扫描"/命令行跑一个 rescan 命令），不做持续文件系统监听——避免正在复制一半的插件文件夹被提前加载这种竞态，代价是"装完新插件要点一下刷新"，不是完全静默的热插拔。**已发现的插件之间启用/禁用是即时的，不需要重启**。
- **校验**：manifest 格式、`api_version` 与当前核心插件 API 版本是否兼容、`requires` 声明的依赖是否都已安装且版本满足。任何一项不过，插件停在 `invalid` 状态，不参与加载，原因要在插件管理器里看得到——不做"能凑合就凑合"的静默降级。
- **加载与生命周期**：`on_load → on_enable`，卸载/禁用走 `on_disable → on_unload`。每一步都在 try/except 边界里，一个插件炸了只把它标成 `failed`，写清楚原因，不牵连其他插件、不拖垮宿主进程——这条直接继承旧项目架构红线"extractor 绝不抛异常"的精神，只是把粒度从"一个提取函数"扩大到"一整个插件"。
- **扩展点注册表**：插件在 manifest 里声明 `provides: [...]`。单例型扩展点（同一时刻只能有一个生效实现，比如 `embedder`、`vector_store`）由配置显式指定"当前用哪个"，多个已启用插件同时声明同一个单例点时**在插件管理器里显式报冲突**，不静默选一个——旧项目"宁可诚实空缺，不产出拼接半成品"原则在这里的体现。多值型扩展点（可以同时存在多个，比如 `extractor:*` 按文件后缀分流、`gui_panel`、`mcp_tool_provider`）则是所有已启用的插件一起参与，核心负责聚合。
- **资源仲裁器（Resource Broker）**：一个通用的、不懂任何 RAG 领域知识的"具名资源租约"机制——插件可以申请一个资源锁（比如 `gpu:0`），核心提供获取/抢占/空闲释放/失败开放（探测失败绝不阻塞）这几个原语。这是把旧项目 `gpu_arbiter.py` 里已经验证过的仲裁策略（同一时刻只让一个模型驻留显存、检索优先级更高的可以抢占、空闲自动卸载、探测失败 fail-open）抽象成一个不专属于 GPU 的通用能力，因为**没有中立的裁判，两个互不知情的插件没法公平抢一块物理 GPU**——这是为什么资源仲裁放在核心而不是某个插件里。

### 2.2 数据流 / 契约管理器（Data Flow & Contract Manager）

负责"数据从哪来、经过谁、到哪去"的强制单向管道，以及**插件唯一被允许读写持久化状态的入口**。详细规则见 [DATA_FLOW.md](DATA_FLOW.md)，这里只说它为什么是核心而不是插件：

- 管道顺序（索引态：发现→抽取→切块→向量化→词法索引→写入→后处理；查询态：解析→检索→融合→重排→标注→响应）只能有**一个权威定义**，如果每个插件自己决定"我执行完该交给谁"，就会退化成旧项目明确要避免的"网状乱接线"。
- 持久化存储（向量库、词法索引、库勾选配置、插件启用状态、缓存）只能有**一个读写入口**。插件不直接开 Chroma/SQLite/JSON 文件，一律通过这个组件暴露的 DataStore API——这直接继承旧项目"文件枚举只走 `collect_md_files` 一个漏斗、裁决只有 `library.decide_included` 一个实现"的纪律，只是把"唯一实现"从函数级提升到组件级。
- **Agent 写权限门禁**也放在这里作为一个可复用服务：把旧项目 `selection_gate.py` / `summary_gate.py` 已经验证过的"提案号+确认码+TTL+一次性"模式抽象成一个通用的"受保护写入"原语，任何插件要接受 AI 触发的写操作都可以直接借用，不用每个插件各自发明一套——这也是"避免功能重复实现"这条约束最直接的落地点。

### 2.3 两个组件之间怎么分工（一句话版本）

插件运行时管**插件本身**（活不活、装没装、谁在占哪个资源）；数据流管理器管**数据本身**（怎么流、谁能碰）。一个插件可以被运行时加载但完全不碰任何持久化数据（比如一个纯展示型 GUI 面板），也可以理论上只处理数据流经过的某一段而对"自己是不是被启用"毫无感知——两者是正交的两个维度，这也是为什么"核心"恰好需要两个组件而不是一个大杂烩。

## 3. 插件运行时形态：in_process vs subprocess_service

旧项目其实已经验证过这个模式——`wemm_server.py`、`mineru_server.py` 都是独立的本机服务进程，懒加载、空闲退出、按需拉起。RAG REDO 把这个模式正式确立为插件的两种合法形态之一：

| 形态 | 适用场景 | 例子（对应旧项目能力） |
|---|---|---|
| `in_process` | 纯 Python、依赖轻量、不容易和核心/其他插件产生依赖冲突 | 文本类提取器（md/txt）、BM25 词法索引、RRF 融合 |
| `subprocess_service` | 依赖重/独立环境（如 MinerU 本机 OCR 需要独立 uv 管理的 py3.12 环境）、需要独占 GPU 显存、或依赖版本容易和核心冲突 | MinerU 本机 OCR、WEMM 页面视觉检索、未来任何"自带一整套模型运行时"的插件 |

`subprocess_service` 插件自带独立的依赖环境（自己的 venv/uv 环境，manifest 里声明启动命令），和核心进程之间走本机 HTTP 或 stdio JSON-RPC 通信——这同时满足"依赖关系独立"（重型/冲突依赖不污染核心环境，插件之间也互相隔离）和"插件化"（这类插件依然遵守同一套 manifest/生命周期契约，只是多声明一个 `runtime.kind`）两条约束。

## 4. 扩展点分类（首版草案，欢迎增删）

| 扩展点 | 类型 | 对应旧项目能力 |
|---|---|---|
| `extractor:<ext>` | 多值 | md/txt 原生、pdf 文字层(pymupdf4llm)、docx(python-docx)、MinerU 云端 OCR、MinerU 本机 OCR |
| `chunker` | 单例 | 现有切块策略 |
| `embedder` | 单例 | BGE-M3 |
| `vector_store` | 单例 | Chroma |
| `lexical_index` | 单例 | BM25 + jieba |
| `fusion` | 单例 | RRF |
| `reranker` | 单例 | 现有 cross-encoder 重排器 |
| `dedup` | 多值 | MinHash+LSH 近似去重 |
| `visual_index` | 多值 | WEMM 页级视觉检索 |
| `library_manager` | 单例（默认自带） | 多库/路径级勾选(`decide_included`) |
| `llm_provider` | 多值 | HyDE、库摘要生成用的 LLM 调用 |
| `gui_panel` | 多值 | 库管理、检索结果、设置页、全库关系图…… |
| `mcp_tool_provider` | 多值 | 现有 9 个 MCP 工具，每个可拆给对应插件自己注册 |
| `import_export` | 多值 | 换电脑搬家的导出/导入 |

不是插件、而是核心提供的**服务**（区别见第 2.2 节）：Agent 写权限门禁、资源仲裁。

**单例扩展点必须支持不重启切换**：`embedder`/`vector_store`/`lexical_index`/`fusion`/`reranker`/`llm_provider` 这几个单例点，只要多个候选实现已经装好并启用，"当前用哪个"只是一条配置，改配置立即生效，不需要重启核心、不需要重装插件——这是"插件化"要真正兑现"能自由换模型"这句承诺的关键，不能因为实现省事就退化成"选了就焊死，换要重装"。`llm_provider` 进一步可以支持"有序回退链"（优先用一个，不可用自动试下一个），参考模板项目已验证过这个模式能显著减少"每个 provider 各写一套可用性探测逻辑"的重复劳动。索引数据要能感知"embedder 换了/版本变了"从而判定过期重算，机制见 [LESSONS.md](LESSONS.md) 第3条。

## 5. 依赖关系独立：重型依赖怎么办，以及绝不污染主机

这条约束是双向的：软件不依赖用户预装的环境，**软件也不能在用户机器上留下自己安装目录之外的痕迹**。两个方向同等重要，后者尤其容易在图省事时被牺牲掉，必须显式设计。

**不依赖**：核心本身只依赖标准库+极少数轻量包（插件加载、清单解析、进程管理）。torch/transformers/chromadb 这类重依赖全部下沉到具体插件的声明里：

- `in_process` 插件的 Python 依赖在核心自己的隔离虚拟环境里安装（默认安装包里预置的"官方插件集"决定了这个 venv 要装哪些包），**不碰用户机器上任何已有的系统 Python 或全局 site-packages**。
- `subprocess_service` 插件自带独立环境，不进核心 venv，插件管理器负责按需下载/引导这个独立环境（比如 MinerU 本机 OCR 插件首次启用时才去下载它自己的 py3.12 环境+模型权重，不在核心安装包体积里）。
- 这样"零依赖安装"说的是**核心+默认插件集**这一层零依赖（打包进单个安装包/便携版），"重型可选能力"仍然会下载，但下载动作被"启用某个插件"这个用户能理解的操作触发，而不是安装期就无差别拉一堆用不上的东西。

**不污染**：安装包不修改用户机器的全局 PATH/环境变量（唯一例外是 Windows 安装包注册自己的开始菜单快捷方式和卸载入口，且卸载时必须清理干净）；所有数据/缓存/模型权重落在本项目自己的 `data/` 目录下；`subprocess_service` 插件产生的子进程必须能被 `on_disable` 干净收掉，不留孤儿进程（旧项目 Flet GUI"关不干净"的教训，见 [LESSONS.md](LESSONS.md) 第6条）。**卸载的定义就是"删掉这个文件夹"或跑一次卸载程序**，之后系统上不应该还留着任何看得见的痕迹。Phase 4 打包阶段要在干净的 Windows 虚拟机上实际验证这一点（见 [ROADMAP.md](ROADMAP.md)），不能只停留在文档里的承诺。
